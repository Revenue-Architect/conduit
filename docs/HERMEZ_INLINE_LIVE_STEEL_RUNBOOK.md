# Inline Hermes run controls and Steel browser

Status (2026-09-28): **inline controls and watch-only Steel viewer implemented; real active-turn/device WebView acceptance and human takeover remain outstanding.** This file retains the original implementation reasoning and now records what actually shipped. Start from `docs/HERMEZ_AGENT_HANDOFF.md` and current source; source wins if this document ages.

## Shipped architecture and evidence

- `chat_page.dart` now composes `StreamingTurnFooter` with `HermesInlineRunSurface` inside `ChatTimelineViewport.liveFooter`. The old floating composer `Positioned` block and its reserved-height calculations were removed. The legacy `HermesLiveActivityDisclosure` class remains test-only, not mounted by ChatPage; its timeline widget is reused by the new surface.
- `hermes_inline_run_surface.dart` is session-keyed and appears only for the exact active Hermes Desktop conversation while running, reconnecting, synchronizing, or locally pending input. It has a bounded real-event timeline, Steer, confirmed Stop, and Review for exact-session pending decisions. The existing resolution sheet and transcript decision cards still own approval submission; dismissal does not deny.
- `hermes_live_run_providers.dart` reads `pendingStoredDecisionsForSession()` from the existing local pending store. This is deliberate: the older `pendingDecisionsForSession()` resumes a Gateway session before reading, an unnecessary and potentially expensive side effect for merely painting chat. Store mutation notifications refresh the inline view without polling; waiting-for-input, state transition, foreground resume, and successful resolution also refresh it.
- `hermes_steel_viewer.dart` stores one optional URL under `PreferenceKeys.hermesSteelViewerUrl`; it is blank by default and editable in Hermes Settings → Live browser. `steelViewerUri()` validates HTTP(S), rejects URL credentials/fragments, preserves existing query parameters, and sets `interactive=false` for viewing. The private tailnet endpoint is not committed as a source default.
- `hermes_steel_live_view.dart` lazily embeds Steel's own debug page in `flutter_inappwebview`; closing the inline browser disposes it. The secondary full-screen view hides the WebView when the exact run is no longer active. No `/cast` client, WebRTC stack, second Gateway socket, backend, or service change was added.
- Tests: focused Hermes/decision/chat ownership 49 passed; new inline/Steel/pending-store 18 passed; timeline/render/turn-state 84 passed. Targeted analyzer of new/touched Hermes UI/store files found no issues; a wider invocation including huge ChatPage/Desktop facade stalled, but Android ARM64 debug build compiled them. APK installed with `adb install -r` on the S25 Ultra and copied to Downloads (`Hermez-inline-live-2026-09-28-arm64-debug.apk`, SHA-256 `6e2d623ea47a5d968a5f9b75ea29576f6df8ab0f3022f26a4eeb1f13cd227793`). Device curl to the installed Steel viewer returned HTTP 200. The phone subsequently entered accidental-touch protection/keyguard lock; no real Hermes active-turn or embedded WebView acceptance was possible. Do not claim otherwise.

## Goal and product boundary

Make the active Hermes conversation the command center for run status, tool activity, pending decisions, Steer, Stop, and an optional live Steel viewer. The chat must remain usable when Steel is unavailable. A separate Live page can remain for expanded details but must not be required for routine control. No new backend, Hermes transport, approval model, browser-streaming protocol, database, or Umbrel/Steel service changes. Non-Hermes chat behavior must remain unchanged.

The target sequence is: Hermes turn starts → one inline run surface appears beneath the active turn → activity/attention/browser can be opened there → actions use the **exact** active Hermes stored session ID → turn completion removes the live surface while preserving the final answer and historical transcript.

## Pre-implementation repository diagnosis (historical)

- Before this change, `lib/features/chat/views/chat_page.dart` mounted `HermesLiveActivityDisclosure` as a `Positioned` widget over the composer. `_messageListBottomPadding()` and nearby scroll-button positioning reserved manually calculated space from `HermesLiveActivityDisclosure.heightFor()` (`collapsedHeight = 72`, `expandedHeight = 292`). This was not a transcript item and has been removed from ChatPage.
- `ChatTimelineViewport.liveFooter` exists in `lib/features/chat/widgets/chat_timeline_viewport.dart`; before this change ChatPage used it only for `StreamingTurnFooter`. It is now the integration point for the single inline Hermes run surface while retaining `StreamingTurnFooter` and its lifecycle/haptics.
- The former `liveFooter` expression was gated by `timeline.runningFooterHost != null`; reconnecting/synchronizing Hermes runs or pending decisions may not have that host. The new expression also derives visibility from exact Hermes session/run and local pending state while preserving non-Hermes behavior.
- `HermesLiveRunPage` currently owns `_steer`, `_stop`, pending-decision loading, and completion presentation. Reuse these service calls; do not duplicate a second run protocol. Pending decisions and resolution already exist in `HermesPendingDecisionStore` and `showHermesAttentionResolutionSheet`.
- No Steel viewer integration existed before this change. `flutter_inappwebview` and Android Internet/cleartext capability were reused; the installed viewer's HTTP reachability is confirmed but real Android WebView playback remains unverified.

## Critical takeover safety finding

`HermesDesktopApiService.steer()` delegates to `_runtimeSteer()` in `hermes_desktop_turn_runtime.dart`. That method returns `true` when the RPC result has `status == 'queued'` (and can also return true after an ambiguous delivery is inferred accepted). **Queued/accepted is not proof Hermes has stopped clicking or typing in Steel.** Therefore the proposed “Steer accepted → immediately enable `interactive=true`” flow is unsafe and must not be shipped as-is.

Before implementing human takeover, establish an observable runtime acknowledgement or confirmed waiting state that proves control has transferred. A generic `waitingForInput` event is sufficient only if tied to this exact browser handoff, not to an unrelated approval. If the installed Hermes/Steel contract offers no such signal, ship watch-only first and keep Take control disabled with an honest explanation. Do not silently race human and agent interactions or create a fake local pause state. Resume likewise needs real acceptance/ownership semantics, not merely a button animation.

## Implementation slices

1. **Inline layout first.** Create one `HermesInlineRunSurface` in the timeline `liveFooter`, composed with `StreamingTurnFooter`. Remove the old floating `Positioned` activity panel, `_liveActivityExpanded` overlay plumbing, activity-specific `_messageListBottomPadding()`/scroll-button offsets, and unused fixed-height calculations only after tests prove the new footer works. Keep one live surface, not a footer plus overlay.
2. **Functional parity.** Add compact running/reconnecting/synchronizing/attention states; expandable bounded event timeline; Steer dialog and confirmed Stop action using `service.steer(sessionId, text)` and `service.interrupt(sessionId)`. Refresh exact-session pending decisions on session change, waiting-for-input, reconnect, foreground resume, and successful resolution; do not poll rapidly. Review opens the existing resolution sheet. Dismissal never means denial. Existing transcript approval/decision cards remain, backed by the same decision store.
3. **Steel watch mode.** Add one locally configurable viewer URL. Do not hard-code the user's private tailnet endpoint in this public-source handoff or infer browser activity from tool-title text. Use Dart `Uri` to preserve existing query parameters and set `interactive=false` for watch. Embed the Steel debug viewer with the existing `flutter_inappwebview`; do not implement `/cast`, WebRTC, frames, tabs, or Steel session management. Lazy-create the WebView only when Browser is expanded and dispose it when closed. Steel failure must not affect Hermes chat.
4. **Expanded browser.** Offer a secondary full-screen viewer reachable from the active chat, with Back returning to chat without stopping Hermes or Steel. Keep the viewer observational by default.
5. **Takeover only after the safety gate above is proven.** An explicit user tap requests Hermes to wait, then the UI waits for confirmed handoff before switching the viewer to `interactive=true`. Rejected/ambiguous/merely queued steer leaves watch mode in place. Resume must return control based on real runtime evidence. If no confirmation contract exists, defer takeover instead of inventing one.
6. **Navigation cleanup.** Demote, but do not initially delete, `HermesLiveRunPage`. Its larger timeline/completion affordances may remain. Only remove any primary Live navigation after proving inline control parity and checking route callers.

The configured viewer URL should be empty/hidden when not set. The user supplied an environment-specific Steel debug viewer address in the originating request; obtain it from the user or a private local setting during implementation. Before coding browser behavior, open that viewer on the S25 Ultra and verify reachability, watch mode, the installed version's `interactive` parameter, and WebView loading of its internal resources. Upstream documentation is guidance; the installed Steel instance is the acceptance target.
